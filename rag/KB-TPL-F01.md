# KB-TPL-F01｜監控通訊中斷與資料缺漏導致誤判與漏報

- 類型：產業典型知識卡（教學範本，非實際案場數據）
- 故障分類：F 監控與資料品質
- 案場：示意案場（教學範本）｜通用｜偏遠 / 多案場集中監控
- 設備 / 失效模式：資料收集器 / RS485 / 4G 路由器｜通訊中斷造成資料缺漏
- 風險：中｜損失型態：診斷失真 + 故障延遲發現
- 現象關鍵字：監控畫面顯示 0 或離線、發電量報表與電表不一致、資料斷點、部分逆變器無資料、時間戳錯亂
- 標籤：SCADA、通訊中斷、資料缺漏、Datalogger、RS485、4G、資料品質、斷訊、時間同步
- 簡報：https://davidyeh51.github.io/pv-8d-management-platform/deck.html?id=KB-TPL-F01

## 一句話結論

資料不可信，所有診斷都不可信；先做資料審計（完整性、量綱、時間戳）再做故障分析，並把「斷訊」本身當成一種需要 8D 的故障。

## SCQA

- **S 情境**：多案場集中監控，維運決策依賴 SCADA 數據。
- **C 衝突**：部分案場資料頻繁中斷，報表發電量低於電表，導致誤派工或漏掉真故障。
- **Q 問題**：是真的不發電，還是資料沒進來？
- **A 答案**：以台電電表 / 逆變器本機紀錄交叉比對，確認為通訊問題；修復通訊鏈並建立資料完整率 KPI。

## 關鍵數據

- 第一步：資料審計（完整性 / 量綱 / 時戳）
- 交叉驗證：電表 vs SCADA（區分真停機與斷訊）
- KPI：資料完整率（每月追蹤）

## 根因

監控資料鏈（電源、網路、匯流排、軟體）任一環節失效，造成資料缺漏或錯誤，使後續分析失真。

## 假說檢定（MECE）

| 假說 | 檢定方法 | 證據 | 判定 |
|---|---|---|---|
| 電源中斷 | 資料收集器電源紀錄 | 斷訊與停電同時 | 待驗 |
| 4G / 網路不穩 | 訊號強度與流量 | 整站同時斷訊 | 待驗 |
| RS485 匯流排問題 | 接線與終端電阻 | 部分設備斷訊 | 待驗 |
| 時區 / 韌體設定 | 時間戳比對 | 資料偏移整數小時 | 待驗 |

## 8D 摘要

- **D0 緊急應變**：確認是否真停機：現場或遠端查看逆變器本機畫面與電表讀值。
- **D1 成立團隊**：R：維運工程師｜C：監控系統商、電信商｜A：監控主管。
- **D2 問題描述**：統計各案場資料完整率、斷訊時段與受影響設備。
- **D3 暫時圍堵**：重啟資料收集器 / 路由器；啟用本機暫存補傳。
- **D4 根因分析**：MECE：電源（UPS / 電源供應器）、網路（4G 訊號、SIM 卡、路由器）、現場匯流排（RS485 接線、終端電阻、位址衝突）、軟體（韌體、時區設定）。
- **D5 永久對策**：修復根因並加裝 UPS、雙網路備援；設定資料收集器斷線補傳。
- **D6 實施驗證**：連續 30 天資料完整率達目標（如 ≥99%）。
- **D7 防止再發**：建立「斷訊 >15 分鐘」告警；月報納入資料完整率；新案場驗收加入通訊壓力測試。
- **D8 結案表彰**：統計因資料問題誤派工次數下降，作為效益。

## 對策

- [立即] 電表交叉比對確認真偽｜成本 低｜避免誤判
- [首選] UPS + 雙網路備援｜成本 低~中｜降低斷訊
- [制度化] 資料完整率 KPI 與告警｜成本 低｜持續監督

## 現場檢查清單

1. 先確認是否真停機
2. 檢查資料完整率與時間戳
3. 比對電表讀值
4. 整站斷 → 查網路/電源；部分斷 → 查 RS485
5. 確認補傳功能啟用

## Lesson Learned

- **L-F01-1 先審資料，再談診斷**：缺漏與時戳錯誤會製造假故障。 → 行動：所有 8D 的 D2 先附資料審計結果。
- **L-F01-2 斷訊本身就是故障**：監控失明期間的真故障會被延遲發現。 → 行動：斷訊 >15 分鐘自動開單。
